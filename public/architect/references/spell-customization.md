# Spell Variant Architect — 強化1〜2項目・弱化1〜2項目のみ改変する設計・検証スキル

## 絶対ルール
CoCシナリオに呪文を登場させる場合、**参照した `呪文一覧.md` 中の既存呪文をベースに、強化1〜2項目・弱化1〜2項目に限定して実質改変したシナリオ固有版を設計する**（計2〜4項目）。単に名称・色・演出・説明文を変えただけでは改変と認めない。**中立の実質改変や5項目以上の実質改変は不可**。変更対象にしなかった効果・コスト・対象・制約などは元呪文のまま保持する。物語上の改変意図が必要。調整された版を元の公式呪文と混同しない（「独自改変／ハウスルール」）。

* まず参照ファイルが**実在し、該当項目を読めること**を確認する。前回の `呪文一覧.md` は現在のスキル一式には同梱されていない。見られないときは原文の効果・数値・存在を推測で埋めず、「要参照」とする。参照できない呪文は「元呪文照合済み」として完成出力しない。
* 元の呪文名と出典／一覧内IDを記録し、**変更前と変更後の比較**を残す。原文の引用は最小限にし、必要なルール要素を要約する。
* シナリオで呪文を使用するすべての重要場面（NPCの使用、PCへの学習、儀式による効果など）で、**どの版の呪文が使われたのか**を固定する。別版に勝手に置き換えない。
* 未確認の版固有ルールや数値、抵抗判定を公式として捏造しない。確認できない情報は未確認と記録し、そのまま完成判定に進まない。

## 改変できる軸（出典の分類や計算規則に従う）
- **効果の強さ**：威力、影響量、効果の確実性、強制力、成功確率
- **効果の広がり**：範囲、射程、持続時間、対象数、対象の意味の拡張・限定（生者／死者／記憶／影など）
- **時間・資源**：詠唱時間、準備期間、MP、SAN、HP、素材、消耗品、協力者、儀式場所
- **条件・反作用**：天候・時刻、儀式環境、失敗時の副作用、術者への反動、再使用制限、対抗・解除手段
- **情報面**：効果の予測可能性、対象選択の確実性、成功に必要な知識や証拠

## 強化・使いやすさ増加には必ず有効な代償をつける
* 変更軸のどれかが**強化（buff）**なら、必ず他の軸で**有意な弱体化・負担増（nerf）**を施し、対応関係を追跡する。複数の強化がある場合、すべての強化に代償を結びつける。対象の意味を拡げる、コストや時間を減らす、成功条件を緩める行為も強化として扱う。
* 代償は実際の物語／セッションで効くものにする。例：長い準備が必要ならNPCの計画と時系列を制約する；高いMPなら誰がどう賄うか説明する；解除しやすくしたならPCがそれを知り実行できる痕跡を用意する。
* **見せかけの代償は不合格**：詠唱時間を延ばしても物語上いくらでも時間がある、SANコストを上げても術者に無制限の資源がある、対象制限が実際の登場人物に影響しない等は補償にならない。
* 単純な単位換算で万能な「バランス点」を捏造しない。MP、SAN、所要時間、持続、対象数、解除可能性は等価ではない。シナリオ状況に応じて定性的比較と試行ケースで検証する。
* **強化0件または弱化0件は不可**。双方1〜2件ずつの実質的な改変が必要。
* 効果の解釈拡張は新しい**対象の定義・境界・除外事例**を明示。元の字面から当然できると断定しない。
* PCが使える場合とNPC専用である場合は、資源状況と実行機会が異なるため別々に評価する。特にMP/SANの負担と回復・供給を検証する。

## 生成→反証→修正の手順
1. **目的確認**：なぜこの場面で呪文が必要か。強く／弱く／使いやすく／使いにくくする狙いを1文で明示する。
2. **元呪文の照合**：`呪文一覧.md` から名称・出典と、わかる範囲の効果・時間・MP・SAN・対象・制約を抽出する。複数候補のときは元呪文を比較して選ぶ。
3. **改変案の生成**：強化を1〜2件、弱化を1〜2件だけ生成する（合計2〜4件）。変更する軸を明示し、それ以外は原呪文どおりとする。強化と制約が実際に釣り合う「組」を作る。
4. **差分台帳**：改変前 → 改変後、buff/nerf、変更意図、物語への影響を記録。変更していない要素は「原典のまま」と明示する。演出だけの差や中立改変は改変件数に数えず、実質差分に追加しない。
5. **代償の紐づけ**：すべての強化に、その強化を制約する弱体化やコスト増を明示的に紐づけ、実際に負担が発生するか確認する。
6. **NPCの知識・改変の由来**：誰が、いつ、なぜ、どの原典呪文を知り、どのような学習・実験・発見を通じて改変したのか。失敗例と痕跡、伝達経路、習得時間、必要資源を検証。改変を知るだけと実行できることを区別する。神話存在から改変版を授けられた場合も人間側の取得・使用経路を検証する。
7. **シナリオへの反映**：制約が時刻や犠牲者選択にどう影響するか／NPCにより良い代替手段がないか／PCが観測・妨害・交渉できるか検討する。
8. **境界試験**：最小／最大対象、最短／最長使用、連続使用、複数術者、想定外のPCの使い方、術者が必要資源を払えない場合、解除・抵抗・失敗を試す。
9. **再帰的反証**：弱点→修正→修正による新しい弱点を発見し、`adversarial-review.md` のゲートまで反復。調整不能なら棄却・前提再構築へ。**未解決の重大な不均衡を残したまま「完成版」としない**。
10. **採用確認**：完成した呪文の派生版もユーザーが採用するまで候補扱い。原典データを書き換えない。

## 品質ゲート（すべて満たす）
- [ ] 一覧にある元呪文を実際に参照・識別した
- [ ] 強化が1〜2項目、弱化が1〜2項目である（実質的な改変は合計2〜4項目）
- [ ] 変更対象以外の効果・コスト・条件・対象・持続・制約は原呪文のまま維持されている
- [ ] 第3の強化・第3の弱化・中立の実質改変がない
- [ ] 「原典／改変」の比較ができ、ハウスルールと明記されている
- [ ] 強化した全項目に、実際に作用する代償・弱体化が対応している
- [ ] 代償を実際の時系列・NPCの資源・PCの介入と照らして検証した
- [ ] NPCが原呪文と改変版を知った・作れた・使えた経緯が成立する
- [ ] 失敗、解除、反復使用、境界事例でも重大な破綻がない
- [ ] 変更によって確定設定や既存の呪文の根拠を無断改変していない

このゲートは自動採点の数値換算では保証できない。`assets/templates/spell-variant.md` と `assets/templates/spell-variant.json` で差分・対応関係を残し、`scripts/validate_spell_variant.py` で構造面を点検する。**機械検査合格＝ゲームバランス保証ではない**。
