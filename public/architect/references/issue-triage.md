# Issue Triage v1.7 — 本当の穴か、既に解決済みか

## 狙い
検証は深く行う一方、**問題を見つけること自体を成果にしない**。問題の指摘前に、現行設定が解決していないかを確認する。「もっと説明できる」「好みが分かれる」は自動的に欠陥ではない。魅力の増える余地と、成立を妨げる不整合を分ける。

## 問題提起の必須手順
1. **最新のユーザー確定事項を再生**：効果、場所、時間、有効期間、NPCの知識、過去の却下案を確認。直近の訂正を最優先にする。
2. **反例を一文で特定**：『設定Aであれば状況Bが生じ、シーンCが成立しない』という形。具体的に示せないなら問題ではなく検討余地に下げる。
3. **既知の制約を代入して解き直す**：裁判開始時に詠唱し、裁判中のみ有効なら、裁判前の心理状態で自動発動するという指摘は**偽陽性（false alarm）**。絶対に「残る課題」として出さない。
4. **重要度を分類**：`resolved`（既存設定で解決）、`false_alarm`（前提の取り違え）、`opportunity`（豊かさ／好みの余地）、`minor`、`major`、`blocker`。`resolved/false_alarm/opportunity` は重大課題数に含めない。
5. **真のmajor/blockerだけ解決**：根本原因に基づく解決を内部で複数検討。構造選択が必要ならユーザー向けに**3案＋影響＋推奨**。小問題ならAIが暫定案に反映し、因果を再検証する。
6. **案の副作用を検証**：新しい能力・要件を勝手に増やしていないか、元の呪文の改変項目が増えていないか。副作用が修復不能なら案を棄却。
7. **報告は本当に必要なことだけ**：既に解決済みの話を長々と繰り返さない。ユーザーから検証を求められた場合は「解決済み→根拠」を簡潔に返す。

## レッドチーム用チェック
- 「敗訴後に詠唱するからテンポが悪い」→詠唱は**開廷冒頭に先行**するとユーザーが確定したなら偽陽性。
- 「裁判より前に敗北を感じても発動してしまう」→場が裁判の開始時に設定され、**裁判中のみ**有効なら偽陽性。
- 「法的な正式な裁判でないと術式が成立しない」→ユーザーが正式性を不要としたなら前提違反。
- 「他人の本心を判定する呪文が必要」→対象本人の敗北認識がトリガーなら前提違反。
- 「敗訴は必須」→ユーザーは**自分が敗北したと対象が認識**することを本質にし、敗訴は一例とした。取り違え。
- 「何を敗北と感じるか自由なら困る」→それ単独では欠陥ではない。NPC人格やPC対抗のゲーム処理が不公平になる**具体的状況**を示せるときに限りissue化する。

## 問題の重要さの検査
問い：「この問題が残ると**誰が、いつ、何を実行できない**のか」「PCが有用な手掛かりを得られないのか」「既知のCoC仕様と矛盾するのか」。答えがないなら検討メモに留める。

## 未確認情報の扱い
根拠資料を読み込んでいない公式呪文について、断定で代替しない。正式な数値・時間が不明でも**創作設計を進めることはできる**が、`未照合／未完成` を維持する。

## 記録
`assets/templates/issue-ledger.md` に問題の反例、依存する確定事項、分類、解消と更新時刻を記録。以前の`resolved/false_alarm`をそのまま新しい課題として再掲しない。
